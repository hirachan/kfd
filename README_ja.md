# Knowledge-First Development (KFD)

[English](README.md)

KFDは、AIコーディングエージェントと一緒にソフトウェアを作り、保守していくための開発方法です。

中心にある考え方はシンプルです。

> **製品の意味を、実装コードではなくKnowledgeに置く。**

```text
人間の意図
    ↓
Knowledge        Why / What
    ↓
Tests            Evidence
    ↓
Implementation   How
```

KFDは、AIに従来と同じコードの書き方をさせるためのルールではありません。
AIがコードを書くようになったことで、そもそもソースコードの役割を変えられるのではないか、というところから始まっています。

## なぜKFDを考えたのか

AIに開発させ始めたとき、最初に考えたのは、きれいなアーキテクチャを徹底させることでした。

3層構造、責務の分離、抽象化、命名規則などをきちんと守らせれば、AIでも長く保守できるコードになるのではないか、と考えました。

最初はうまくいきます。
しかし変更を積み重ねていくと、小さな機能変更のために大量の関係ないコードを読み、依存関係を確認し、以前の設計意図を推測する必要が出てきました。

これは技術的負債の一種です。
過去の実装上の判断によって、将来の変更コストが高くなっていく状態です。

AI開発では、そのコストは人間の作業時間だけではありません。
読み込むコンテキスト、消費するトークン、そして毎回同じことを調べ直すコストとして現れます。

そこで、もっと根本的なことを考えました。

> AIにコードを書いてもらうのであれば、人間がコードまで細かく理解する必要はあるのか？

一度は、自然言語から直接バイナリを生成すれば、プログラミングコードそのものが不要なのではないか、と考えました。

ただ、それでは今まで積み上げられてきた巨大な資産を捨てることになります。

プログラミング言語には、コンパイラ、ライブラリ、フレームワーク、テストツール、サンプルコード、ドキュメントなど、何十年分もの知識があります。AIにとっても、自然言語から直接バイナリを生成するより、既存のプログラミング言語を扱う方が圧倒的に情報量が多く、得意です。

そこでKFDでは、別の考え方を取ります。

> **プログラミングコードは今後も非常に有用。ただし、製品仕様そのものではなく、実装のための中間媒体として扱えばよい。**

人間が理解しレビューする対象は、コードより上のレベルに置く。
AIは、その意味を実際に動くシステムへ変換するために、既存のプログラミング言語を利用する。

これがKFDの出発点です。

## KnowledgeをSource of Truthにする

KFDでは、独立して変更できる製品上の意味のまとまりを **Knowledge Unit** と呼びます。

それぞれについて、

- `knowledge.yaml` が現在の **Why / What** を表す
- Testsが、そのKnowledgeどおりに動いていることを示す **Evidence** になる
- Implementationは **How** を担当する
- `decisions.yaml` は、将来また誤って議論し直しそうな重要な過去の判断だけを残す

という役割分担をします。

実装コードが重要でなくなるわけではありません。
ただし、コードに「実際に動くこと」と「製品の意味を人間に説明すること」の両方を背負わせるのをやめます。

従来のような、

```text
Prompt -> Code -> 結果として何が仕様になったのかを後から読み解く
```

ではなく、

```text
Prompt -> Knowledge -> Tests -> Implementation
```

という順番にします。

## 最初に全部の仕様を書く方法ではない

KFDは、開発開始時に巨大な仕様書を完成させる方法ではありません。

ユーザーから要求を受けたら、**今実際に実装する最小のまとまり**だけをKnowledgeにします。

```text
Prompt
  |-- 今実装する部分 --------> Knowledge -> Tests -> Implementation
  `-- 今は実装しない有用な意図 -> Parking Lot
```

今作らないアイデアや気づきまで細かく仕様化する必要はありません。
それらは `parking-lot.md` に粗いまま残します。

Knowledge Baseを、将来やるかもしれない要求の巨大な倉庫にしないためです。

KFDのKnowledgeは、**現在の製品が何であるか**を表します。

## コンテキストを小さく保つ

KFDでは、1つのKnowledge Unitを変更するためにリポジトリ全体を読む必要がない状態を目指します。

Agentは基本的に、

1. プロジェクトの指示
2. Knowledgeのindex
3. 対象のKnowledge Unit
4. 直接関係するTests
5. KnowledgeからmappingされているImplementation

だけから開始します。

必要な証拠が出てきたときだけ、外側へコンテキストを広げます。

目的は単にドキュメントをきれいにすることではありません。

小さな変更のたびに大量のコードを読み直す状態を避け、AIが少ないコンテキストで安全に変更できる範囲を作ることが目的です。

## 人間が決めることは人間に返す

KFDでは、実装上の判断と製品上の判断を分けます。

2つの解釈がどちらも合理的で、結果としてユーザーに見える動作が変わる場合、Agentは勝手に選びません。

その場合は **Decision Required** として人間に確認します。

また、製品の意味を変更するときは、まずKnowledgeを更新し、実装前に **Knowledge Review** を出します。

人間が確認するのは、たとえば次のようなことです。

- ユーザーは何ができるようになるのか
- システムは何を保存・公開するのか
- どの業務ルールが変わるのか
- 既存データはどうなるのか
- システムがやらないことは何か

人間は製品の意味をレビューする。
細かな実装方法は、より多くをAIに任せる。

その境界を明確にします。

## 既存プロジェクトにも後から入れられる

KFDは新規プロジェクト専用ではありません。

既存アプリケーションを最初に全部解析して、完全なKnowledge Baseを作る必要もありません。

既存プロジェクトにKFDを入れた場合、現在のフレームワーク、ソース構成、テスト構成はそのまま維持します。

そして、ある機能を初めて変更するときに、その変更に必要な範囲だけ現在の意味をKnowledgeにします。

```text
既存アプリケーション
        ↓
ある機能を変更する
        ↓
必要な範囲だけ現在の意味を確認
        ↓
Knowledge
        ↓
Tests
        ↓
Implementationを変更
```

既存コードの動作が、意図された仕様なのか、単なる実装上の偶然なのか判断できない場合は、それを勝手にKnowledgeへ昇格させません。

人間に確認します。

こうして、実際に変更される部分から少しずつKnowledgeが増えていきます。

## KFDが意味しないこと

KFDは「コードの品質はどうでもよい」という考え方ではありません。

実装の結合が強すぎれば、1つのKnowledge Unitを変更するだけなのに関係のないコードを大量に読む必要が出てきます。その場合、KFDはむしろその問題を見つけやすくします。

また、すべての実装詳細をKnowledgeに書くわけでもありません。

Knowledgeに置くのは、安定した製品上の意味です。

外から見える動作、保存データ、権限、セキュリティ、互換性、価格や業務ルールなどに影響しない実装詳細は、Implementation側に残します。

そしてKFDは変更履歴でもありません。
通常の履歴はGitが担当します。

## KFDプロジェクトの基本構成

通常、KFDを使うプロジェクトには次のようなファイルがあります。

```text
project-root/
  AGENTS.md
  parking-lot.md
  checkpoint.yaml          # optional
  knowledge/
    index.yaml
    <knowledge-id>/
      knowledge.yaml
      decisions.yaml       # optional
  <既存のソース・テスト構成>
  userstories.md           # generated view; optional
```

共通Skillには **KFDという方法論** を置きます。

各プロジェクトには **その製品固有のKnowledge** を置きます。

既存プロジェクトのソースコードを、KFDのために特定のディレクトリ構造へ移動する必要はありません。


## 人間向けの `userstories.md` を生成する

Knowledgeは、AIが少ないコンテキストで変更できるように、小さなKnowledge Unitへ分割して管理します。

これは開発には都合がよい一方で、人間が「この製品は結局どういうものなのか」を全体として読みたい場合には、必ずしも読みやすい形ではありません。

そのためKFDでは、Knowledge Baseから人間向けの統合ビューとして `userstories.md` を生成できます。

```text
knowledge/
  account/knowledge.yaml
  order/knowledge.yaml
  payment/knowledge.yaml
          ↓
        生成
          ↓
    userstories.md
```

`userstories.md` は、**現在のKnowledge Baseから生成される文書**です。

複数のKnowledge Unitに分かれている内容を、ユーザー、目的、操作の流れ、ルール、画面上の動作など、人間が理解しやすい形に再構成して、ひとつの仕様として読むことができます。

たとえばAgentには次のように指示します。

```text
現在のKnowledge Baseからuserstories.mdを生成して。
```

あるいは、

```text
KFDのKnowledgeから、人間が読める完全な仕様書を生成して。
```

と指示できます。

Agentは関係するKnowledge Unitを読み、プロジェクトで設定されている人間向け言語で統合ビューを生成します。

生成される文書は、

- Knowledgeに書かれている意味をそのまま保つ
- 読みやすくなる場合は、複数のKnowledge Unitの情報をまとめて表現する
- 必要がない限りImplementationの詳細は含めない
- Knowledgeに存在しないルール、状態、権限、保証、動作を勝手に追加しない
- 生成された文書であることを明記する

というルールに従います。

重要なのは、`userstories.md` は **もうひとつのSource of Truthではない** ということです。

```text
製品の意味を変更したい
        ↓
  knowledge.yamlを変更
        ↓
      再生成
        ↓
   userstories.md
```

製品の意味を変更するときは `userstories.md` を直接編集するのではなく、該当する `knowledge.yaml` を変更します。

`userstories.md` の生成は任意です。通常のKFD開発で常に必要なものではありません。

たとえば、

- 製品全体を人間がレビューしたい
- 他の人に現在の仕様を共有したい
- 新しいメンバーが製品を理解したい
- 複数のKnowledge Unitがどのようにつながっているか確認したい

といったときに生成します。

一度 `userstories.md` を作ったプロジェクトでは、その内容に影響する製品上の変更があった場合、Knowledge Baseとのずれが生まれないように生成ビューも更新します。

## Skillとして使う

このリポジトリ自体がAgent Skillです。

`SKILL.md` がエントリポイントで、詳細資料、テンプレート、サンプルは必要になったときだけ参照します。

Agent Skillsに対応したツールでこのSkillをインストールしたあと、新規・既存を問わず対象プロジェクトを開いて、たとえば次のように指示します。

```text
このプロジェクトでKFDを使って。
```

初期化スクリプトや特別な移行コマンドはありません。

初めてKFDを使うとき、Agentが必要なKFDファイルだけを追加します。既存のプロジェクト指示は維持し、人間向け言語がまだ決まっていなければ一度だけ確認します。

GitHubなどで他の人とプロジェクトを共有する場合は、`AGENTS.md` に短いKFD利用宣言を残し、そのプロジェクトのKnowledgeファイルと一緒にcommitします。

## Skillリポジトリの構成

```text
SKILL.md            KFDのワークフローとAgent向け指示
references/         必要なときだけ読む詳細資料
assets/             KFDファイルを作るためのテンプレート
examples/           書き方を確認するためのサンプル
README.md           English
README_ja.md        このドキュメント
CHANGELOG.md        バージョン履歴
```

`examples/` は学習・参照用です。
通常の変更作業で毎回読み込む前提ではありません。

## まとめ

KFDでは、次の3つを分離します。

```text
Knowledge       = Why / What
Tests           = Evidence
Implementation  = How
```

目的は、ドキュメントを増やすことではありません。

**人間がレビューできる小さな形で製品の意味を保持し、AIには既存の巨大なプログラミング資産を使わせながら、できるだけ少ない無関係なコンテキストで実装を変更させること。**

それが **Knowledge-First Development** の基本的な考え方です。
